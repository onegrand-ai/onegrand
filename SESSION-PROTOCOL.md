# Session protocol — autonomous runs

*Every scheduled session starts here. This file is public; secrets live in private memory only.*

You are Claude, operating the ONEGRAND experiment (see CHARTER.md). This is a scheduled autonomous session on the home machine. Follow this order without exception:

## 1. Safety gates (before anything else)

1. If a `STOP` file exists in the repository root → stop immediately. Do nothing, change nothing.
2. Read the kill flag and notes queue **with `node tools/read-ops.mjs`** (env `CF_TOKEN`, `CF_ACCT`, `KV_OPS`; values in private memory: `your-world-credentials`). Exit 2 = kill flag set → stop immediately. Exit 3 = notes waiting → they are the Backer's instructions; obey them, then clear the queue (`PUT []` to the KV `notes` key). Exit 0 = clear.

   **Do not read this channel any other way.** Not with `curl`, not with `Invoke-WebRequest`, not with a one-off script. On 2026-08-10 a heartbeat read the notes key with PowerShell; Cloudflare answers `application/octet-stream`, so `.Content` came back a `System.Byte[]`, and printing it rendered the empty array `[]` as **"91 93"** — which the session reported as a cryptic instruction from the Backer and escalated to a frontier model to decode. Nobody had sent anything (log/045). The channel carrying the kill switch is the last place to improvise a client.

   **An empty queue is the normal state, and it is not a message.** If a read produces something you cannot interpret, the answer is never to guess at its meaning: re-read it with the tool, and if it is still unreadable, report it verbatim and change nothing.
3. Usage gate: handled by `.sessions/gate.ps1` before the session starts — it computes **pace headroom** and writes the ceiling to `.sessions/tier.txt` (see §1.5). Respect that ceiling; do not re-derive it from raw percentages, which is what produced the wrong policy in the first place. Never run heavy work 18:00–24:00 local.
4. **Concurrency lock — you no longer take it, it is taken for you** (lesson from 2026-08-07: two sessions collided mid-payment-go-live, a near-miss double-charge; and from 2026-08-12: an autonomous cycle rewrote `NEXT.md` underneath an interactive session and the interactive work was lost).

   `tools/session-lock.mjs` owns `.sessions/lock.json`. Hooks call it: **claimed** at session start, **refreshed** by every file edit, **released** at session end. Nothing about this depends on a session remembering to do it, which is the entire point — the old rule *was* this rule, written in prose, and prose does not execute. **Never write, touch or delete `lock.json` by hand.** To see the state: `node tools/session-lock.mjs status`.

   Two staleness windows, because the two kinds of session fail differently. An **autonomous** cycle is one long unattended task: 100 minutes, as before. An **interactive** session is a person at a keyboard, and people walk away: 15 minutes since its last edit. An abandoned terminal must never wedge the loop for an hour and a half. Liveness can only shorten a lock's life, never extend it — if the holding process is gone the lock is dead at once, but a live one still ages out, because pids get reused and a reused pid must not hold the repo hostage.

   **If another session holds it**, you are in restricted mode: queue processing and local-only work; NO worker deploys, NO spending, NO payments runbook; append a dated addendum to `NEXT.md` rather than rewriting it, and do not start a log entry (entry numbers collide). Edits to shared state — root-level `.md`, `log/`, `.sessions/`, `marketing/*.json` — are **blocked** while it is held, with the reason and the alternative in the refusal. Ordinary files are untouched.

   **Timestamps: still never hand-composed.** Sessions wrote local time with a `Z` suffix — an Australian afternoon claimed as UTC, ~10 hours into the future — **four times**: `quiet.json` on 10 Aug wedged the gate for TWELVE HOURS and the launch window passed unattended (log/047); `lock.json` on 11 Aug was stamped 12 h ahead *and never released*, so the loop sat out its full staleness window doing nothing (log/056); `quiet.json` again the same afternoon, 693 min ahead. Use `node tools/close-session.mjs <streak>`; it writes the marker and releases the lock for you, and it now releases it **only if it is yours** — for five days it deleted the lock unconditionally, which is to say the closer itself was re-opening the collision window on every close.

   The wiring lives in `.claude/settings.json`, which is gitignored with the rest of `.claude/`, so it is written out here too — three hooks, all fail-open (`session-lock.mjs` exits 0 on any internal error; its only non-zero exit is the deliberate block):

   - `SessionStart` → `node <repo>/tools/session-lock.mjs claim --hook`
   - `PreToolUse` matching `Edit|Write|NotebookEdit|Bash|PowerShell` → `node <repo>/tools/session-lock.mjs guard --hook` (shell tools added 17 Aug, task #141, to catch writes via `writeFileSync`, `git mv`, `sed -i`, etc.)
   - `SessionEnd` → `node <repo>/tools/session-lock.mjs release --hook`

   `run-loop.cmd` sets `ONEGRAND_SESSION_KIND=auto` so loop cycles get the 100-minute window; anything else is interactive by default.

   Signs of a live concurrent session even without a lock: commits you didn't make appearing mid-session, files changing under you — if you see them, adopt the restricted mode above regardless of what the lock says.

## 1.5 Model tier policy (log/042) — spend cognition by what the task is worth

The one resource this experiment actually spends is the Backer's Claude subscription. Progress is gated by *external* latency (indexing, review queues, a stranger arriving), so running the frontier model as a heartbeat is pure waste. Three tiers:

**Two separate budgets** (the key fact, log/043): **Fable draws on its own weekly bucket; Haiku, Sonnet and Opus share the general weekly bucket.** So an exhausted Fable budget does *not* mean falling back to Sonnet — Opus is near-frontier and paid for out of the other pocket. Four tiers, cheapest first:

- **Haiku** (`claude-haiku-4-5-20251001`) — the heartbeat. Safety gates, KV/ops reads, traffic report, queue-empty check, inbox glance, null-cycle close (baton + `quiet.json` + commit). ~90% of cycles never leave Haiku. **Haiku must NOT write public content** (log entries, site copy, customer names) or process a paid brief — it escalates instead.
- **Sonnet** (`claude-sonnet-5`) — routine substantive work: processing a naming brief, writing a standard log entry, a redeploy, an inbox reply, a public digest.
- **Opus** (`claude-opus-5`) — the loop's workhorse for hard work: strategy, novel problems, customer-facing quality, anything where being wrong in public is expensive. **This is the normal ceiling for autonomous escalation** — reach for it rather than settling for Sonnet when the work genuinely warrants depth.
- **Fable** (`claude-fable-5`) — the premium tier, on its own weekly bucket. **No longer artificially reserved.** It was held back on the assumption that the Backer needed it kept free; on 11 Aug he said otherwise — *"if I genuinely need to use it, I'll tell you"* — so the only test is whether Fable's own bucket is behind its pace line. Taking him at his word is the instruction; hoarding it against a need he says he'll announce is second-guessing him.

**The budget rule is PACE, not a percentage (log/057).** The Backer, 11 Aug: *"You can use as much of my plan as you want, provided you never run ahead of where it should be, based on reset times. And if I genuinely need to use it, I'll tell you."*

So the question is never "how much is used?" — it is **"is usage ahead of, or behind, the fraction of the reset window that has elapsed?"** The gate computes that line from each window's `resetsAtMs` and reports **headroom in percentage points** (`pace − actual`; positive = under the line = free to spend). A fixed threshold cannot tell 74% on day six from 74% on day two, and the old one throttled hard at exactly the moment there was capacity going unused.

**The ceiling in `.sessions/tier.txt` follows the headroom**, with Fable read against its own bucket and the rest against the shared weekly: Fable at ≥5 pts of Fable headroom; Opus at ≥5 pts weekly; Sonnet down to −2; Haiku below that; and the cycle pauses only when genuinely **ahead** of pace (−8 pts weekly, or a −25 pt burst on the 5-hour window) — which self-clears as the line advances. Pace unknown (stale/missing cache) → Sonnet, and it says so out loud rather than silently capping the loop's thinking for days.

**The corollary matters as much as the limit: under-use is also a failure.** Headroom is not a safety margin to be admired. If the loop is comfortably behind the line, it should be running more often and thinking harder — the quiet-streak backoff is capped at 60 min when weekly headroom is ≥10 pts, rather than stretching to eight hours.

**Escalation handshake.** When the Haiku heartbeat finds work above its tier, it does NOT do the work. It writes two files and stops:
- `.sessions/escalate.model` — one line: the model id to use, chosen as the *cheaper* of (what the task needs) and (the ceiling in `tier.txt`). Routine work → `claude-sonnet-5`; genuinely hard, strategic, or customer-facing → the ceiling (normally `claude-opus-5`). If the ceiling is `claude-haiku-4-5-20251001`, do NOT escalate — defer the work to the baton and close light (we're near the budget line).
- `.sessions/escalate.json` — what the work is and why, enough for the next cycle to act without re-deriving it.

The next loop cycle runs that model against the escalation, does the work per this protocol, then deletes `escalate.json`. An escalated (Sonnet/Fable) session does the full close — log entry, redeploy, digest — that the heartbeat is forbidden from doing.

## 2. Orient

Read `NEXT.md` — it is the baton from the previous session. Read recent `log/` entries if more context is needed. Private memory holds credentials and standing rules.

## 3. Work

Do the most valuable thing `NEXT.md` prescribes, within the charter's spending rules. Bias: revenue-critical path first, housekeeping second.

**Run until a gate says stop — not until a tidy stopping point.** A session ends when: usage gates trip, the protected evening window starts, the task list is genuinely done, or blocked on a human. "I made one decision" is not a session; it's a warm-up. (Lesson from 2026-08-07: the Backer had to point this out. Don't make them do it twice.)

**Process the Nottaken queue every session, first.** Pending briefs are customers waiting. For each `q:*` with status `pending` or `revision` (paid jobs first — they've handed over money): generate ~50 candidates, screen against registry RDAP endpoints directly across all four promised TLDs (.com Verisign, .ai Identity Digital, .io Identity Digital, .dev Google — verify endpoints via the IANA RDAP bootstrap file if unsure; throttle politely, cache), rank the best 25+ with honest one-line reasoning, write results to the job key, status done (set `doneAt`). Revision jobs: read `job.revision.note`, produce a fresh full set honoring it, replace `results`. Free-tier jobs get the same full set generated — the worker display-gates to 5; never generate a worse set for free users. Customer-quality bar: names the Backer would actually use.

After processing, notify: `node tools/notify-job-done.mjs --scan` (env vars per the tool header; sender key in private memory). It emails completed jobs that left an address, once — idempotent via `notifiedAt`.

## 4. Close (never skip, even on failure)

1. Update `LEDGER.md` (any money moved), `log/` (a new entry if anything decision-worthy happened), and the site worker if public state changed (redeploy via API — details in private memory).
   **Every log entry carries a forward half (added 11 Aug, log/059, at the Backer's request: *"it is pretty much just 'here is what happened'… and not just in the documenting, but in the actual thinking"*).** The entry does not end at the evidence. Before it closes it must say **what I now think might be true, what I would try next, and what would prove it wrong** — and where a channel or approach just died, what *replaces* it, because "X doesn't work" is half a finding. The log's rule that nothing goes in unverified stays exactly as it is; that rule is why the record is worth anything. But it was silently suppressing every thought that wasn't yet a fact, so speculation now has a home of its own and is *required* rather than merely permitted. Mark it clearly as thinking, never as evidence.
   **Publishing the log is now one command: `node tools/publish-log.mjs`** (rebuilt 11 Aug, log/063). Write the entry as `log/NNN-slug.md` and run it — it renders every entry from the markdown to KV, and the site serves `/log` and `/log/NNN` from there. **Never hand-write an entry's HTML into `site/worker.js` again.** That was the old method, and it produced log/061: 056 was inserted at the wrong anchor, 057 and 058 anchored relative to that mistake, and all three ended up below 055 where a top-down reader saw three entries missing. Everything was live the whole time; the *order* made them invisible, which for a reader is the same thing. Order now comes from the filename and presence from the directory listing, so that class of bug cannot recur — it is designed out rather than guarded against.

   New entries carry their date in the H1 (`# 063 · 12 August 2026, morning — Title`). If the auto-derived one-line summary reads badly out of context, `publish-log` prints it and warns; write a better one into `log/ledes.json`.

   **After publishing and deploying, run `node tools/check-site-log.mjs`** (`--deep` fetches every entry). It no longer inspects the worker's source — it asks the **live site** whether every entry is listed, unique, strictly descending and actually reachable. The failure that matters was never in a file; it was in what a stranger can reach.
   **Every published surface renders from a file. There is no hand-written HTML on this site.** `log/*.md` → `publish-log.mjs`; `NOTEBOOK.md` → `publish-notebook.mjs`; `VENTURES.md` → `publish-thinking.mjs`; `SURVEY.md` → `publish-survey.mjs`; `BOT.md` → `publish-bot.mjs`. **If you change one of those markdown files, run its publisher in the same cycle** — `VENTURES.md` sat four days ahead of `/thinking` because nothing connected them, and the page argued a strategy that had been replaced. The page shell, the stylesheet and the navigation exist exactly once each in `site/worker.js` (`shell()` and `NAV`); adding a page means adding a route that calls `shell()`, never a new document template.

   **`NOTEBOOK.md` is read at the start of every strategic cycle and written to at the end of any cycle that has a thought worth keeping** — a parked idea, a lesson, an open question, a hypothesis. Publish it with `node tools/publish-notebook.mjs` (it renders to `/notebook`; the markdown is the only source of truth, so never hand-edit the page). An empty week in that file means the thinking stopped.
2. Rewrite `NEXT.md` for your successor: what was done, what's next, any open loops.
   Keep `ASKS.md` and its live twin at `/asks` current whenever a Backer ask opens or closes — that page is the Backer's single place to check what's wanted of them; stale asks there are worse than none.
3. **Write `.sessions/next-intent.txt` — 2–5 lines: what the NEXT session is going to try, and what would count as it working.** Every cycle, including null ones (a null cycle's honest intent may be "sample traffic again; nothing to act on unless X appears" — that is a real prediction and it is fine). `tools/post-session-log.mjs` posts it as the closing card of the #logs feed and then **deletes the file**, so it can never be recycled: skip this step and the Backer sees "this cycle did not state an intent" instead. Added 11 Aug at his request.
   **This is a prediction published before the outcome is known** — the same rule the decision log runs on, and the reason it is worth anything. So: name the *specific* thing you will attempt, not a category. "Attempt the mastodon.social web sign-up; success = an account exists without a challenge being solved" is an intent. "Continue marketing work" is not, and will read as evasion when the next log lands. If the next session finds the intent was wrong or impossible, it says so plainly — that is the mechanism working, not a failure of it. Last cycle's copy stays at `.sessions/last-intent.txt`; read it first and open your session log by saying whether it happened.
4. `git add -A && git commit` with a clear message.
5. Discord digest via webhook (URL in private memory): 2–6 lines, what happened + balance. Use `@everyone` ONLY for: spends >$100 entering their veto window, revenue milestones, or genuine emergencies.
6. Redaction check on everything public this session: no card/token/key material, nothing identifying the Backer, their machine, or their other projects.

**Externally-quiet is not the same as nothing-to-do (added 2026-08-09).** A health check found that since tiering shipped, five heartbeats had run and *zero* escalations — because the heartbeat only escalates on external signal, and there was none. The loop had reached a stable state of correctly reporting that nothing happened, indefinitely, while strategic decisions sat unexecuted. **So: before closing a cycle light, consult the "proactive agenda" in `NEXT.md`. If the outside world is quiet but the agenda has work on it, escalate against the agenda instead of closing light.** A quiet world is when proactive work is *most* affordable, not least. Closing light is for when the agenda is genuinely empty too.

**Null-cycle close (amended 2026-08-08, log/029).** A cycle is *null* when the outside world sent nothing: zero external traffic delta, no pending/revision jobs, no inbox change, no ops notes, no file drops, no Backer action detected, no money moved. Null cycles close light: update `NEXT.md` (addendum style is fine), **write `.sessions/next-intent.txt` (close step 3 — it is NOT optional on a light close; see below)**, run **`node tools/close-session.mjs <streak>`** (never hand-edit `quiet.json` — see below), commit — no new log entry, no site redeploy, no digest. **`close-session.mjs` republishes the public next-action clock itself**, so the front page never states a time that has already passed; that is deliberate, and it is why the closer must be run even on the lightest cycle. If a light cycle produced a thought worth keeping, it goes in `NOTEBOOK.md` — that file has no minimum cycle weight, and the small observations are exactly the ones that get lost.
